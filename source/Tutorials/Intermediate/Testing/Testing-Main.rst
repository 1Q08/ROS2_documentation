测试
====

为什么需要自动测试？
--------------------

以下是我们应该有自动化测试的许多充分理由中的一些：

* 你可以更快地对代码进行增量更新。
  ROS 有数百个包，具有许多相互依赖关系，因此很难预测一个小改动可能引起的问题。
  如果你的改动通过了单元测试，你可以更确信你没有引入问题——或者至少问题不是你的错。
* 你可以更自信地重构代码。
  通过单元测试验证了你在重构时没有引入任何错误。
  这给了你远离变更恐惧的美妙自由！
* 它会导致更好的代码设计。
  单元测试迫使你编写代码，使其更容易被测试。
  这通常意味着保持你的底层函数和框架分离，这是我们在 ROS 代码中的设计目标之一。
* 它们防止反复出现的错误（错误回归）。
  为你修复的每个错误编写单元测试是一个好习惯。
  事实上，在你修复错误之前编写单元测试。
  这将帮助你精确地，甚至确定性地重现错误，并更精确地理解问题是什么。
  因此，你还将创建一个更好的补丁，然后你可以用你的回归测试来验证错误已修复。
  这样，如果代码后来被修改，错误就不会意外地重新引入。
  这也意味着，将更容易说服补丁的审阅者问题已解决，并且贡献是高质量的。
* 其他人可以更容易地处理你的代码（文档的自动形式）。
  当你进行更改时，很难弄清楚你是否破坏了别人的代码。
  单元测试是其他开发人员验证他们更改的工具。
  自动测试记录你的编码决策，并自动向其他开发人员传达他们的违规行为。
  因此，测试成为你代码的文档——大多数时候不需要阅读的文档，当确实需要检查时，测试系统会精确地指出要读什么（哪些测试失败）。
  通过编写自动测试，你让其他贡献者更快。
  这改善了整个 ROS 项目。
* 如果我们有自动化单元测试，成为 ROS 的贡献者要容易得多。
  新的外部开发人员很难为你的组件做贡献。
  当他们修改代码时，他们常常是在盲目地进行，由大量的猜测驱动。
  通过提供自动化测试的测试套件，你帮助他们完成任务。
  他们的更改会得到即时反馈。
  为项目做贡献变得更容易，新贡献者更容易加入。
  而且他们的第一批贡献质量更高，这减少了维护者的工作量。
  双赢！
* 自动测试简化了维护工作。
  特别是对于成熟的包，它们变化较慢，而且大多需要更新到新的依赖，自动测试套件有助于非常快速地确定包是否仍然工作。
  这使得决定包是否仍然受支持变得容易得多。
* 自动测试放大了持续集成的价值。
  回归测试，连同正常的基于场景的需求测试，为你组件的整体自动化测试体系做出贡献。
  你的组件能更好地针对它所依赖的其他 API 的演变进行测试（CI 服务器会更好更精确地告诉你代码中出现了什么问题）。

也许编写测试最重要的好处是测试使你成为一个好公民。
测试长期影响质量。
这是许多开源项目中公认的做法。
通过编写回归测试，你正在为 ROS 生态系统的长期质量做贡献。

这一切都是免费的吗？
--------------------

当然，天下没有免费的午餐。
要获得测试的好处，一些投入是必要的。

* 你需要开发一个测试，有时可能困难或昂贵。
  有时它也可能不是微不足道的，因为测试应该是自动的。
  如果你的测试涉及特殊硬件（它们不应该：尝试使用仿真，模拟硬件，或将测试缩小到更小的软件问题）或需要外部环境，例如人类操作员，事情会变得特别棘手。
* 回归测试和其他自动测试需要维护。
  当组件的设计改变时，大量测试会失效（例如它们不再编译，或抛出与 API 设计相关的运行时异常）。
  这些测试失败不仅是因为重新设计重新引入了错误，还因为它们需要更新到新设计。
  偶尔，在更大的重新设计中，旧的回归测试应该被丢弃。
* 大量的测试可能需要很长时间来运行，这会增加持续集成服务器的成本。
